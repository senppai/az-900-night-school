🛡️Azure access and security

RBAC, Zero Trust, defense-in-depth, encryption with Azure Key Vault, and Microsoft Defender for Cloud — plus a light contrast with Policy and locks so you do not mix the three tools.

  • ✦Defense-in-depth as stacked layers, not one magic product
  • ✦What Microsoft Defender for Cloud is for — and how RBAC differs from Policy and locks

🛡️Identity proved who you are. Security is what happens next: what you are allowed to do, how Azure thinks about trust, how layers pile up, and which service watches your security posture. The exam loves mixing these names. We will keep them in separate drawers.

Picture an office building. The badge at the door is authentication (last lesson). Your job title — receptionist, electrician, CEO — is authorization. Azure's job-title system is role-based access control. Around that sit two bigger ideas: never assume the person in the hallway is safe (Zero Trust), and never rely on a single lock (defense-in-depth).

1. Azure role-based access control (RBAC)

Azure RBAC is authorization: who can do what, on which scope. You assign a role to a user, group, or service principal, at a management group, subscription, resource group, or single resource. Built-in roles you will see on the exam include Owner (full control, including access), Contributor (create and manage, but not grant access), and Reader (look but do not change). The habit Microsoft wants is least privilege: the smallest role on the smallest scope that still gets the job done.

Think

RBAC = job title + floor of the building. Owner / Contributor / Reader are the titles. Management group → subscription → resource group → resource are the floors.

2. Zero Trust

Old model: if you are on the corporate network, we trust you. Zero Trust says the opposite. Never trust, always verify. Being “inside” is not enough. Every request is checked. Three phrases show up again and again: verify explicitly, use least privilege, assume breach. MFA, Conditional Access, and tight RBAC are how Azure puts that idea to work — but Zero Trust itself is the model, not a single checkbox named Zero Trust.

  • ▹Verify explicitly — authenticate and authorize using all the signals you have (identity, device, location, risk).
  • ▹Least privilege — just enough access, just in time, just the right scope.
  • ▹Assume breach — design as if an attacker is already inside, so one stolen password is not the whole company.

Think

Zero Trust is a castle where even the king shows a badge at every door. It is a strategy, not a product SKU.

3. Defense-in-depth

Defense-in-depth means stacked layers. If one layer fails, the next one still has a chance. Azure describes layers from the physical datacenter up through identity, perimeter, network, compute, application, and data. A firewall alone is not defense-in-depth. MFA plus NSGs plus encryption plus RBAC plus physical security — that is the model.

4. Encryption and key management

Encryption scrambles data so only someone with the key can read it. Azure talks about two states. Encryption at rest protects stored data — Azure Storage, managed disks, and Azure SQL Database encrypt data at rest by default with Microsoft-managed keys. Encryption in transit protects data moving across a network — TLS/HTTPS for web traffic, plus encrypted tunnels like VPN Gateway. If you must control the keys yourself (for compliance), you can use customer-managed keys stored in Azure Key Vault.

Azure Key Vault is the safe for secrets: application secrets (connection strings, passwords, API keys), cryptographic keys, and TLS/SSL certificates. Apps fetch what they need at runtime instead of hard-coding a password in a config file, access is controlled with Entra ID and RBAC, and every use is logged. Managed HSM is the option when you need keys held in dedicated hardware security modules.

At rest

Data sitting on disk

  • • Storage, disks, databases
  • • On by default with Microsoft-managed keys
  • • Customer-managed keys optional

In transit

Data moving on a network

  • • TLS / HTTPS
  • • VPN Gateway tunnels
  • • Protects against eavesdropping

Azure Key Vault

Where keys and secrets live

  • • Secrets, keys, certificates
  • • Access via Entra ID + RBAC
  • • Audited every time it is used

Exam trap

Key Vault stores secrets; it does not encrypt your whole storage account by itself, and it is not an identity provider. And “encrypted at rest by default” does not make your data public-proof — access is still your job.

5. Microsoft Defender for Cloud

Microsoft Defender for Cloud is Azure's cloud security posture and workload protection service. It looks at how you configured things, gives you a Secure Score, and recommends fixes (turn on MFA, close a public storage account, patch a VM). It can also protect workloads — servers, databases, containers — in Azure and, with extra setup, in hybrid and other clouds. Think of it as a security advisor that also helps shield the workloads, not as RBAC and not as a firewall you draw on a VNet.

Think

Defender for Cloud = “how secure is my estate, and what should I fix?” Azure Advisor also gives security tips, but Defender for Cloud is the dedicated security posture and protection service.

6. RBAC vs Policy vs locks (light contrast)

Three tools sit near each other on the exam. They are not interchangeable. You will meet Policy and locks in more depth in the governance lesson. For now, only the contrast matters.

RBAC

Who can do what

  • • Assign roles to people and apps
  • • Owner, Contributor, Reader, and many more
  • • Scoped to MG / subscription / RG / resource

Azure Policy

What is allowed

  • • Rules such as “only these regions”
  • • Can audit or deny non-compliant resources
  • • About configuration, not job titles

Resource locks

Cannot delete (or cannot change)

  • • CanNotDelete or ReadOnly
  • • Even an Owner must remove the lock first
  • • A padlock, not a permission set

Exam trap

RBAC does not stop someone with Contributor from deleting a VM they are allowed to manage. A lock does. Policy does not assign the Contributor role. RBAC does. If the question is “who may create VMs,” that is RBAC. If it is “nobody may create VMs in East US,” that is Policy. If it is “do not let anyone delete this production vault,” that is a lock.

AZ-900 exam points

  • ★RBAC = authorization: roles + scope, least privilege
  • ★Zero Trust = never trust, always verify (verify explicitly, least privilege, assume breach)
  • ★Defense-in-depth = many layers, so one failure is not game over
  • ★Microsoft Defender for Cloud = security posture (Secure Score) and workload protection
  • ★Do not confuse Defender for Cloud with Entra ID or with Azure Policy

One sentence to remember

RBAC decides who can do what at which scope, Zero Trust refuses to trust a request just because it is “inside,” defense-in-depth stacks layers so one failure is not fatal, and Defender for Cloud scores and helps protect the estate — while Policy and locks handle allowed configuration and delete protection, not job titles.

Exam-style scene · Exam-style scene

A security lead wants a single Azure service that shows a Secure Score, flags a storage account that is open to the internet, and can add extra protection to VMs and databases.

Pick: Microsoft Defender for Cloud

That is posture management plus workload protection. Advisor gives broader recommendations including cost. RBAC only assigns roles. Conditional Access only evaluates sign-ins.

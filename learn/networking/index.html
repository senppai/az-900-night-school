🌐Azure networking fundamentals

VNets, subnets, peering, Azure DNS, VPN Gateway versus ExpressRoute, and public versus private endpoints.

🔌If compute is where code runs, networking is how that code talks to users, to on-premises, and to other Azure services. AZ-900 keeps this at the map level: private networks, name resolution, and two ways to plug the office into Azure.

1. Virtual networks and subnets

An Azure virtual network (VNet) is your private network in Azure. You pick a private IP address space (for example 10.0.0.0/16) and a region. Resources such as VMs get private IPs from that VNet. A subnet slices the VNet into smaller ranges so you can separate workloads — web tier in one subnet, data tier in another — and attach different network security groups. Subnets live inside one VNet. You cannot stretch a single VNet across two regions; for two regions you create two VNets and connect them.

Think

VNet = your private network in Azure. Subnet = a slice of that network.

2. VNet peering

VNet peering connects two Azure virtual networks so resources can talk using private IPs. Traffic stays on the Microsoft backbone — it is not hairpinned out to the public internet. You can peer VNets in the same region or in different regions (global peering). The VNets stay separate management objects; you are not merging them into one giant VNet. Address spaces must not overlap.

Exam trap

Peering is not a VPN Gateway and it is not ExpressRoute. Peering links Azure VNets to each other. VPN/ExpressRoute link Azure to somewhere else (usually on-premises).

3. Azure DNS

DNS turns names into IP addresses. Azure DNS is a hosting service for DNS domains that runs on Azure’s name servers. You can host a public zone (contoso.com on the internet) or a private zone that resolves names only inside your VNets (app.internal.contoso). On the exam, Azure DNS is the answer when the need is “host and resolve DNS names in Azure,” not when the need is “connect two networks.”

Think

Azure DNS = name tags. VNet = the private streets. They solve different problems.

4. VPN Gateway vs ExpressRoute

Both connect on-premises networks to Azure. They do it very differently. Azure VPN Gateway creates an encrypted tunnel over the public internet (site-to-site for offices, point-to-site for individual laptops). It is usually faster to set up and cheaper. ExpressRoute is a private connection through a connectivity provider. Your traffic does not travel over the public internet. You get more reliability, more consistent bandwidth, and often lower latency — at higher cost and with more setup. Encrypted-over-internet vs private-circuit is the distinction Microsoft wants.

Azure VPN Gateway

Encrypted over the internet

  • • IPsec/IKE tunnels across the public internet
  • • Site-to-site or point-to-site
  • • Good starting hybrid option; bandwidth and latency depend on the internet

ExpressRoute

Private connection

  • • Dedicated circuit via a provider; not the public internet
  • • More consistent performance and higher bandwidth options
  • • More cost and lead time; used when internet VPN is not enough

Exam trap

ExpressRoute is not “a faster VPN.” It is a different path: private connectivity. VPN Gateway still uses the internet; it just encrypts what it sends.

5. Public vs private endpoints

A public endpoint is an address reachable from the public internet (a public IP on a VM, or the public HTTPS URL of a storage account). A private endpoint gives a PaaS service a private IP on your VNet using Azure Private Link. Traffic to that storage account or database then stays on the private network instead of going out to a public hostname. Use public when the service must be reached from the internet. Use private when you want the service to look like it lives on your LAN.

AZ-900 exam point

  • ★VNet / subnet — private address space in Azure
  • ★Peering — VNet to VNet on the Microsoft backbone
  • ★Azure DNS — host and resolve names
  • ★VPN Gateway — encrypted hybrid over the internet
  • ★ExpressRoute — private hybrid connection
  • ★Private endpoint — private IP for a PaaS service in your VNet

6. Basic network access controls

Once resources are on a VNet you need to decide what traffic is allowed. A network security group (NSG) is a list of allow/deny rules (source, destination, port, protocol) attached to a subnet or a NIC — the basic filter that says “allow 443 from the internet, deny everything else.” Azure Firewall is a managed, stateful firewall service for the whole network: central rules, application (FQDN) filtering, threat intelligence, logging. Azure DDoS Protection defends public endpoints against distributed denial-of-service floods; a basic level is always on for the platform, and the paid tier adds tuning, alerts, and cost protection for your resources.

NSG

Simple allow/deny rules

  • • Attached to a subnet or NIC
  • • Port, protocol, IP rules
  • • Free, basic filtering

Azure Firewall

Managed central firewall

  • • Stateful, whole-network
  • • FQDN and threat-intel filtering
  • • Paid, centrally logged

DDoS Protection

Stop traffic floods

  • • Protects public IPs
  • • Absorbs volumetric attacks
  • • Not a rule-based filter

Exam trap

An NSG does not stop a DDoS flood, and DDoS Protection does not decide which ports are open. Rules → NSG or Firewall. Floods → DDoS Protection.

One sentence to remember

A VNet with subnets is your private Azure network, peering joins VNets on Microsoft’s backbone, Azure DNS resolves names, VPN Gateway encrypts hybrid traffic over the internet, ExpressRoute uses a private connection instead, and private endpoints put PaaS services on a private IP in your VNet.

Exam-style scene · Exam-style scene

A bank must connect its datacenter to Azure with a dedicated circuit that does not travel over the public internet, and it wants the Azure SQL database to be reachable only via a private IP on the VNet.

Pick: ExpressRoute plus a private endpoint for Azure SQL.

ExpressRoute is the private on-premises path. A private endpoint gives the database a VNet IP. VPN Gateway would still ride the public internet, and a public endpoint would keep the database on the internet.

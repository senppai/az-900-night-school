💻Azure compute: VMs, containers, and functions

How Azure runs your code — virtual machines, containers, and Functions — plus VM options, the parts of a VM, and where web apps should live.

18 min read

  • ✦When to choose a VM, a container, or Azure Functions
  • ✦What VM Scale Sets, availability sets, and Azure Virtual Desktop are for
  • ✦Which extra resources a virtual machine needs
  • ✦How App Service, containers, and VMs compare as app hosts

Why this shows up on AZ-900

Match the compute type to the amount of control you want. Full OS control → VM. Package the app, skip the OS → container. Run a small piece of code when an event happens → Functions. Host a website without babysitting servers → App Service.

⚙️Compute is “where the code runs.” Azure gives you a spectrum: rent a whole computer, pack the app in a container, or hand Microsoft a function and let events wake it up. AZ-900 wants you to pick the right height on that spectrum.

1. Three compute types

A virtual machine is Infrastructure as a Service. You pick a size (CPU and memory), an OS image (Windows or Linux), and you patch and configure that OS. A container packages your app plus its libraries, without a full guest operating system for every copy — lighter, faster to start, easier to ship the same way everywhere. Azure Functions is serverless compute: you write a function, bind it to an event (HTTP call, queue message, timer), and Azure runs it. You do not manage servers, and you typically pay when the code actually runs.

Virtual machines

IaaS — you manage the OS

  • • Full control: custom software, specific OS settings
  • • You patch, back up, and size the machine
  • • Heaviest operational work, most flexibility

Containers

App + dependencies, not a full OS each time

  • • Consistent package from laptop to Azure
  • • ACI for simple jobs; AKS when you need an orchestrator
  • • You manage the app image, not a whole Windows/Linux VM OS

Functions

Serverless — event-driven snippets

  • • No servers to patch
  • • Scales automatically with events
  • • Best for short tasks, not a giant always-on monolith

Think

VM = rent a computer. Container = ship the app in a box. Function = run this code when X happens.

2. Virtual machine options

Azure Virtual Machines are the individual IaaS computers. Azure Virtual Machine Scale Sets (VMSS) let you run a group of identical VMs that grow and shrink automatically — the exam picture for autoscale at the VM layer. An availability set places VMs in the same region across fault domains (different racks / power) and update domains (staggered host patching) so one rack or one host update does not take every VM down. Availability sets are the older in-datacenter high-availability pattern; availability zones are separate buildings. Azure Virtual Desktop (AVD) is Windows desktops and apps streamed from Azure — a desktop-as-a-service, not just “a VM you RDP into.”

Exam trap

An availability set is not an availability zone. Sets spread VMs inside a datacenter. Zones spread them across datacenters in the region.

AZ-900 exam point

  • ★Need many identical VMs that autoscale → VM Scale Sets
  • ★Need VMs to survive rack failure / host updates in one region → availability set
  • ★Need Windows desktops for remote users → Azure Virtual Desktop
  • ★Need one custom server you fully control → a regular Azure VM

3. Resources a VM needs

A VM is never just a CPU slider. At fundamentals level, remember the bundle: a VM size (vCPUs and memory), an OS disk (and optional data disks), a network interface (NIC), and a virtual network plus subnet for that NIC to plug into. You often add a public IP if it must be reached from the internet, and a network security group to filter traffic. The VM also needs an identity (admin username/password or SSH key) and sits in a resource group and region like everything else.

  • ▹Compute: VM size — vCPU and memory
  • ▹Storage: OS disk, optional data disks
  • ▹Network: NIC, virtual network, subnet; optional public IP and NSG
  • ▹Identity & place: admin credentials, resource group, region (and maybe a zone or availability set)

4. Application hosting options

When the question is “where should this web app run?”, Azure still offers three big answers. Azure App Service hosts web apps and APIs as Platform as a Service — you bring the code (or container), Microsoft handles the web server, patching, and scale. Containers (App Service, Azure Container Apps, Azure Container Instances, or AKS) fit when the app is already packaged as an image. Virtual machines fit when you need a custom runtime, unsupported OS settings, or software that expects a full machine. Same website, three levels of control.

Think

Web app, do not want servers → App Service. Already in a container image → containers. Need a full custom OS → VM.

5. AI, machine learning, and IoT/Edge categories

The compute module now ends with a quick tour of three service families. You only need the category and the classic use case. Azure AI services (formerly Cognitive Services) are prebuilt AI models you call through an API — vision, speech, language, translation — no data science degree needed. Azure AI Foundry is the place to build and run generative AI apps with large models. Azure Machine Learning is the platform for data scientists to train, deploy, and manage their own models. Azure IoT Hub connects, monitors, and manages millions of IoT devices, and Azure IoT Edge runs cloud workloads (including AI) on the devices themselves, close to the data.

If the scenario says… think…

NeedCategory / service
Call an API to read text in photos or transcribe speechAzure AI services (prebuilt models)
Build a chat app on a large language modelAzure AI Foundry / Azure OpenAI
Data scientists train and deploy their own modelsAzure Machine Learning
Connect and manage thousands of sensorsAzure IoT Hub
Run analysis on the factory device, even offlineAzure IoT Edge

Exam trap

Prebuilt API (AI services) vs build-your-own model (Machine Learning) is the distinction to hold onto. IoT Hub is the cloud side; IoT Edge is the device side.

One sentence to remember

VMs give you a full computer that needs CPU, memory, disks, and a NIC on a VNet; scale sets add identical autoscaling copies; availability sets spread VMs inside a datacenter; Virtual Desktop streams Windows workspaces; containers package apps; Functions run event-driven code; and App Service is the usual PaaS home for a web app.

Exam-style scene · Exam-style scene

A team has a .NET website, does not want to patch Windows Server, and needs the site to scale when traffic spikes. They are not bringing a custom kernel module.

Pick: Azure App Service (a web app).

App Service is PaaS hosting for web apps. A VM would work but adds OS homework. Functions are a poor fit for a full website. Scale Sets are the VM-level autoscale answer, not the “we don’t want servers” answer.
